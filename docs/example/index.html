yaml-v3-node-decode-drops-knownfields: A custom UnmarshalYAML that calls node.Decode into a struct loses the outer decoder's KnownFields: a mistyped key loads silently. Check keys yourself

---

config.Load decodes with KnownFields(true), so an unknown key anywhere in seamless.yaml is refused. That stops inside a custom UnmarshalYAML(*yaml.Node): node.Decode(&someStruct) there runs a fresh decoder WITHOUT KnownFields, so a mistyped key decodes with no error and the field stays zero.

This was found 2026-11-13 in the AAR B design (note 01M7C9TQH76XF1D59P3N18EHP9) and handled in cc638e0e (config.RestrictedAccount). For a restricted entry the silent zero fails open: {account: X, exlude: [...]} would load as a plain entry, which is the account's full reach.

How to apply:

  • In a config type with its own UnmarshalYAML, walk the MappingNode's keys against an allow-list and refuse an unknown one with its name and key.Line.
  • Decode each value separately (scalar into string, sequence into []string), never the whole mapping into a struct.
  • Resolve alias nodes first (resolveAlias in internal/config).
  • Pin it with a test that loads a typo and must fail. TestPeerAuth_RestrictedShapes "a mistyped exclude" does this, and it was shown to fail with the check removed.

Related: yaml-v3-refuses-bare-int-into-duration.

The owner's shell is zsh. Unlike bash, zsh does not split an unquoted parameter expansion on spaces. With FILES="a b c", git add -- $FILES receives one argument "a b c", and set -- $spec does not split either.

What happens: the command fails or matches nothing. A script with no set -e carries on: on 2026-11-12, during a /seam-fanout commit gate, a temporary index stayed at HEAD, and a worktree was built at the base tree instead of the intended commit tree. A path-set diff caught it before any gate ran.

How to apply:

  • Keep path lists in a file, one per line, and run xargs -n 50 git add -- < list.txt.
  • Or use a real array, or ${=VAR} (zsh-only), or run the snippet under bash -c.
  • After building a tree to gate, assert its changed path set equals the intended list (git diff --name-only A B | sort | diff - list) before trusting the result.

SQLite uses a partial index only when it can prove, at prepare time, that the query's WHERE implies the index's WHERE.

What fails: a query that binds the column, claude_session_id = ?, never implies claude_session_id <> '', because the parameter is unknown when the statement is prepared. The planner reports SCAN sessions exactly as if the index did not exist.

Found: 2026-11-12, migration 039 (plan fenced-sessions P1). The suggested index ON sessions(external_client, claude_session_id, created_at) WHERE ambient = 0 AND claude_session_id <> '' was refuted by EXPLAIN QUERY PLAN on the real query. Migration 010's idx_sessions_ambient_external_identity has the same <> '' shape. It is unique for integrity, so it still enforces correctly, but it cannot serve WHERE ambient = 0 lookups.

How to apply:

  • For a lookup index, make the partial WHERE use only conditions the query states as literals (for example ambient = 1 with a query that says ambient = 1), or make the index non-partial. 039 chose non-partial: idx_sessions_conversation (external_client, claude_session_id, created_at, id).
  • Pin it in a test: EXPLAIN QUERY PLAN on the exact production query must show USING INDEX <name>. TestMigration039_ConversationLookupsUseTheirIndexes is the model.

Most seamlessd subcommands call store.Open, which runs migrations, against whatever the default config names (~/.config/seamless/seamless.yaml, so ~/.seamless/seam.db). A dev or branch build run from a repo or worktree with no SEAMLESS_CONFIG therefore migrates the live database under the running daemon. seamlessd approvers <verb> --help counts: it opens the database before it validates its arguments.

How to apply: always run a built seamlessd with SEAMLESS_CONFIG pointing at a scratch config, even to read its help, and prefer /usr/bin/env -i HOME=<scratch> PATH=/usr/bin:/bin SEAMLESS_CONFIG=<scratch config>. Read flags from the source instead when you can. To inspect the live database use sqlite3 "file:$HOME/.seamless/seam.db?mode=ro". Code fix is filed under plan seamless-sealed-unlock.

Incident, 2026-11-09 03:15:45Z (session cc/7238e932): a locked-projects build applied migrations 29-36 to the live ~/.seamless/seam.db via approvers enroll-code --help. The live daemon (commit 13444ec) compiles only up to 28; main has up to 30; 31-36 exist only on locked-projects.

State after it, checked read-only: additive only (new empty tables; new columns that are nullable or NOT NULL DEFAULT ''), no rows changed or removed, no positional INSERT or SELECT * on the altered tables at 13444ec. The daemon kept serving and task writes at 03:20:51Z landed. A daemon restart on this schema was NOT tested; at 13444ec migrate() skips versions at or below the applied maximum and has no refusal for a newer schema.

Consequences while it holds:

  • seamlessd doctor from an older binary warns that the schema is ahead.
  • Archives taken from this database record schema v36, and a binary compiled below that refuses to restore them, by the newer-schema refusal in internal/store/migrate.go.
  • Do NOT add a migration on main numbered 31-36 before locked-projects merges without repairing this database first: migrate() would skip it here. Renumbering the branch's migrations would re-run its CREATE TABLEs against tables that already exist and break startup.
  • Editing migrations 31-36 on the branch before merge will not reach this database.

Open: the owner decides whether to leave it (it matches once locked-projects ships) or roll back, which means stopping the daemon and hand-reversing the DDL. Update this memory when that is settled.

What Task Scheduler does (lab detached-updater-os-spikes, a Windows 11 test machine, build 26200, S4U stand-in)

  • Task actions run under the Schedule service's svchost.exe, in ONE job shared across tasks. Its only limit flag is SILENT_BREAKAWAY_OK, and Task Scheduler toggles even that. No KILL_ON_JOB_CLOSE.
  • Stop-ScheduledTask, schtasks /End and taskkill /F of the daemon end ONLY the action process. Children survive whatever their creation flags (plain, DETACHED, NO_WINDOW, BREAKAWAY).

  • It came back healthy in 0.81s, against 5.81s for the task path.
  • It is windowless: CREATE_NO_WINDOW children showed no console window. An InteractiveToken task launching the console-subsystem seamlessd.exe likely shows one; that is unverified, and the post-release check covers it.
  • Its start is certain: CreateProcess succeeds or fails synchronously. schtasks /Run rc=0 does not prove a start (0x41303, "has not yet run"), and a task that never runs never reaches a fallback.
  • The task path gains nothing on the job: a task-launched updater lands in the same shared job as the daemon anyway.

As built

Spawn (from inside seamless.service)

  • Run systemd-run as a child, buffer its output, Wait with a ~30s timeout (it returns in 3-25ms). rc=0 means the unit was created and exec'd. Whether the update worked comes only from the attempt record.
  • rc != 0 -> notify-only. stderr classes (substring match):

    • "already loaded or has a fragment file": this attempt's unit exists; never respawn under that ULID.
    • "Failed to find executable": the binary is missing.

  • --collect removes the unit whatever the outcome. Without it, a failed run blocks the name until reset-failed. RuntimeMaxSec is enforced (SIGTERM, then SIGKILL after TimeoutStopSec); 1800s is twice the installer timeout. KillMode=control-group also reaps the installer's leftovers when the updater exits.

Environment

  • The transient unit gets the USER MANAGER's environment, never the daemon's: HOME, PATH (as short as /usr/local/bin:/usr/bin), XDG_RUNTIME_DIR, LANG, USER, LOGNAME, SHELL, plus DBUS_SESSION_BUS_ADDRESS only where a user bus exists.
  • No SEAMLESS_CONFIG, hence --config is load-bearing. Nothing from seamless.service's Environment= or drop-ins arrives either (a proxy, for one).
  • Pass what the updater needs explicitly, and only for values the daemon has set and non-empty: --setenv=HTTPS_PROXY=... etc. (HTTP(S)_PROXY, NO_PROXY, ALL_PROXY in both cases, SSL_CERT_FILE, SSL_CERT_DIR).

  • Setsid or plain child: KillMode=control-group SIGTERMs the whole service cgroup on restart and stop, then SIGKILLs at the stop timeout (systemd-cgroup-kill-reaches-setsid-children).

What launchd actually does to a LaunchAgent's children

  • The job's main process is a process-group leader (pgid = pid) in launchd's session (sid = 1, not its own).
  • On bootout, kickstart -k (which sends SIGTERM, not SIGKILL), kill -9 of the main process, and the 5s exit-timeout SIGKILL alike, launchd sends SIGTERM to the job's process group when the main process goes. It never escalates to SIGKILL for leftover group members, and it does not kill by coalition or session, although each job has its own resource/jetsam coalition.
  • A plain child (exec.Command with no SysProcAttr) is in that group, so it gets the SIGTERM. Go's default handling would end the updater mid-install.
  • A child started with Setpgid or Setsid gets no signal and is reparented to pid 1.
  • The orphan can run the installer's launchctl bootout + bootstrap on its own service. launchd logs "bootout initiated by: launchctl<-sh<-updater<-seamlessd(service)" and accepts it.

Decision for 2.09 (darwin)

  • Spawn the updater with SysProcAttr{Setsid: true} (the plan's choice; Setpgid alone would also survive) and reap it with go cmd.Wait(). The installer child keeps installerProcAttr's Setpgid.
  • outsideServiceCheck on darwin: unix.Getpgid(0) == os.Getpid(). Being a process-group leader means not being in the service's group, and that group is the only set launchd signals.
    • True for the Setsid child and for a transient job's main process; false for a plain child.
    • Do NOT use XPC_SERVICE_NAME: children inherit the service's label, and an orphan also has ppid 1, so both of Detect's gate-9 signals match an orphaned updater. updaterProbe already forces Supervised for that reason.
  • Fallback (works, not needed on 27): a transient job whose plist lives in <data_dir>/update/ (0600 in 0700), bootstrapped into gui/<uid>.
    • It runs as its own job: own XPC_SERVICE_NAME, ppid 1, pgid = pid. BTM never touches it.
    • It stays loaded as "not running" after it exits, so boot out any leftover label before the next bootstrap.

The user's shell is zsh 5.9 on macOS, with the EQUALS option on (the zsh default). Equals-expansion rewrites any unquoted word that begins with = into the path of the command named after it: =ls -> /bin/ls. If no such command exists, zsh aborts the line before it ever runs.

So == is not a plain operator token in zsh -- it is a word starting with =, and it gets expanded (to a lookup of the command =), which always fails:

% echo ==foo
zsh: =foo not found
% [ a == a ] && echo ok
zsh: = not found          # the word `==` expands, nothing runs

Verified 2026-08-18 on zsh 5.9.

How to apply -- when writing a shell command for this machine:

  • Prefer [[ ... == ... ]]. Inside [[ ]] zsh does not equals-expand, so [[ $a == $b ]] works (and == there is a glob match, not a string compare).
  • With the [ builtin or test, use = instead: [ "$a" = "$b" ].
  • If a literal == really must be an argument (an awk/jq/grep expression, a --opt==value, a URL or query string), quote it: [ a '==' a ], awk '$1 == "x"'. Quoting suppresses the expansion entirely.
  • The same trap applies to any argument beginning with =, not just ==.

This is the same family of quoting hazard as the existing global rule "quote every glob and URL argument" in ~/.claude/CLAUDE.md.

Why: it is a repeating mistake -- an unquoted == looks like valid bash/POSIX but fails immediately under zsh, and the error message (= not found) does not obviously point at the real cause.

Plan: Background update check + automatic updates (Claude Code-style)

Context

Today Seamless updates only when someone runs seamlessd update, which re-runs the Sigstore-verified installer, or remembers seamlessd update --check. The docs ask users to update weekly because releases land often, so installs drift. Goal: Seamless keeps itself current the way Claude Code's native install does:

  • it checks by itself;
  • it applies in the background and takes effect with a ~2s restart at a quiet moment;
  • it says so afterwards;
  • it can be turned off;
  • package-manager and source builds are told about updates, never touched.

Owner decisions (2026-10-09)

  1. The check runs inside the daemon (startup, then every few hours) against the GitHub releases API. There is no separate OS-scheduled job and no self-hosted manifest.
  2. Auto-apply is on by default for installs made by the curl/PowerShell installer. These are notify-only: Homebrew, make install/go install source builds, client-only machines (no daemon) and unknown layouts.
  3. Restart when idle, with a deadline: no live agent session and nothing in flight. If an update has been pending more than 24h, take the next lull in requests.
  4. A 24h soak. Auto-apply only takes releases at least update.min_age (24h) old, so a bad release can be pulled first by marking it prerelease. Manual seamlessd update and console "Update now" ignore the soak.
  5. LAN-shared servers follow the same rules. The idle gate already counts remote sessions.

Constraints carried in

  • One upgrade implementation. Apply = the existing path: verify the installer's Sigstore bundle in-process (update_verify.go), then run the installer. No fetch/swap/service logic in Go (memory seamlessd-update-command).
  • macOS needs a full reload after a binary swap. A swapped binary needs launchctl bootout + bootstrap, never kickstart -k (memory macos-26-amfi-...). docs/install still kickstarts after bootstrap (install:611); that gets fixed here.
  • No telemetry. The check is one anonymous GET: fixed UA, no token, no identifiers. update.check: false means zero update traffic.
  • Config files are never edited. Present-but-invalid values are errors. Old binaries reject unknown keys (KnownFields).
  • Console rules. Cookie POSTs pass the CSRF origin check, and pages morph in place without a reload.
  • The signer pin is arctop-only. Every release auto-update can target or roll back to is at or above the floor release (the first release carrying Phase 2), so it is arctop-signed.
